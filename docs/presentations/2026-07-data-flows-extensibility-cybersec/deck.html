Ροές δεδομένων

Ρόλοι & κοινή χρήση δεδομένων

Τρεις ρόλοι, αυστηρά διαχωρισμένα δεδομένα. Η κοινή χρήση γίνεται μόνο μέσα από δύο ελεγχόμενους μηχανισμούς — ποτέ με «γυμνά» IDs.

Policyholder

Ιδιοκτήτης δεδομένων

Κάθε Policy, έγγραφο, gap και score δένεται σε ownerUserId. Όλα τα queries φιλτράρουν στην ιδιοκτησία του καλούντος.

Agent

Πρόσβαση μέσω σχέσης

Βλέπει δεδομένα πελάτη μόνο μέσω ενεργού CustomerRelationship ή ρητού AccessGrant (πρόσκληση από τον πελάτη).

Admin

Λειτουργικός ρόλος

Gated σε layout, middleware και API (roles:['admin']). Κάθε admin ενέργεια περνά από verifyAdminRole() και activity log.

Μηχανισμοί κοινής χρήσης

  • AccessGrant — ρητή, ανά-συμβόλαιο παραχώρηση πρόσβασης με scope policy:<id>, μέσω πρόσκλησης με token.
  • CustomerRelationship — η σχέση agent↔πελάτη ανοίγει τα collaboration threads, τα προτεινόμενα προϊόντα και τα renewals· ο κεντρικός έλεγχος assertThreadAccess επιβεβαιώνει τη συμμετοχή και στις δύο πλευρές.

Συμβόλαιο ποιότητας για κάθε endpoint

  • Zod validation σε κάθε input· τυποποιημένα responses (createApiResponse / createApiError).
  • Policy inventory: κάθε route έχει καταχωρημένο auth mode, methods και controls στο api-route-policy-inventory.json — το CI μπλοκάρει αποκλίσεις (audit:api-auth).
  • Rate limiting global στο edge + αυστηρότερα profiles σε 35 ευαίσθητα routes.

Επεκτασιμότητα

Σημεία επέκτασης & integrations

Σήμερα σε λειτουργία

  • Inbound webhooks — Stripe billing, RevenueCat (mobile-ready), signed job triggers.
  • Pluggable AI providers — Gemini / Anthropic / OpenAI πίσω από κοινό interface· εναλλαγή με ένα env key, mock provider για CI.
  • Scheduled jobs API — renewals, weekly digest, churn prevention, protection-score refresh: όλα admin-gated /api/v1/jobs/* endpoints, καλούμενα από cron.
  • Bulk import — μαζική εισαγωγή πελατολογίου για agents.

Σχεδιασμένη επόμενη φάση

  • QStash async queue — αποσύνδεση του AI pipeline από το request path για κλίμακα.
  • Partner API keys — machine-to-machine auth για ασφαλιστικές / brokers πάνω στο υπάρχον /api/v1.
  • OpenAPI spec — παραγωγή από το route inventory, ώστε τεκμηρίωση και CI audit να έχουν κοινή πηγή.
  • Insurer data feeds — απευθείας εισαγωγή συμβολαίων χωρίς PDF, πάνω στο ίδιο analysis pipeline.

Η αρχιτεκτονική «route inventory + guards + versioning» σημαίνει ότι νέο integration = νέο route + μία γραμμή στο inventory — το CI επιβάλλει τα υπόλοιπα.

Άμυνα σε βάθος: 4 στρώματα ελέγχου

Κάθε στρώμα επαληθεύει ξανά ταυτότητα και ιδιοκτησία. Η παράκαμψη ενός ελέγχου δεν αρκεί για πρόσβαση σε δεδομένα.

1 · Edgeproxy.ts: global rate-limit (Upstash), Supabase session check, RBAC redirects ανά ρόλο, security headers & CSP με origin παραγόμενο από env
2 · ApplicationProtected layouts ξανακαλούν getAuthenticatedUser()· admin layout ελέγχει ρόλο· server actions με auth guard πριν από κάθε data access
3 · APIrequireApiUser({ roles }) σε κάθε route, Zod σε κάθε input, signature verification στα webhooks, CI-enforced policy inventory
4 · DataOwnership scoping σε κάθε Prisma query (ownerUserId / relationship / grant), Prisma singleton, pooled συνδέσεις, secrets μόνο σε env

Κυβερνοασφάλεια

Ταυτότητα, πρόσβαση & έλεγχος IDOR

Authentication

  • Supabase Auth με password + magic links· redirect allowlist κλειδωμένη στο live site.
  • Email verification με δικό μας token flow μέσω Brevo· hard gate έτοιμο πίσω από ENFORCE_EMAIL_VERIFICATION flag.
  • Sessions σε httpOnly cookies — καμία αποθήκευση tokens στον browser.

Authorization

  • RBAC σε τρία επίπεδα: middleware routing, layouts, API guards.
  • Ownership scoping: τα δεδομένα φιλτράρονται στη βάση με το ID του καλούντος — όχι έλεγχοι μετά την ανάγνωση.

Συστηματικός έλεγχος IDOR (05/2026)

Ελέγχθηκαν 395 Prisma queries σε 85 αρχεία + και οι 19 server-action files για guards και ownership. Τα ευρήματα κατηγοριοποιήθηκαν (Critical → Low) με συγκεκριμένα fixes· οι ασφαλείς επιφάνειες τεκμηριώθηκαν ρητά. Ο έλεγχος επαναλαμβάνεται σε κάθε νέα επιφάνεια δεδομένων πριν το launch sign-off.

Secure SDLC: η ασφάλεια ως CI gate

Blocking checks σε κάθε commit

  • audit:api-auth — κανένα route χωρίς δηλωμένη πολιτική auth.
  • type-check (strict) + lint + unit tests (145/145) + production build.
  • verify:migrations — schema και migrations πάντα σε συγχρονισμό.
  • i18n / UTF-8 checks — καμία διαρροή hardcoded strings ή mojibake.

Λειτουργική ετοιμότητα

  • Sentry server + browser (tunnel για anonymous)· καθημερινό synthetic launch check.
  • Incident runbooks: auth session, billing webhook failure, AI provider degradation, localization regression.
  • Compliance evidence: DSR e2e, billing rollback drill, SRE restore drill — αρχειοθετημένα ανά κύκλο (GR-GA-2026.03).
  • Audits: IDOR + AI advice compliance στο docs/audits/.
