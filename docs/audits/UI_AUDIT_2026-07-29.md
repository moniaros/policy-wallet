# UI/UX, theme, accessibility & responsive audit — 2026-07-28/29

Triggered by a production screenshot: the `/wallet/[id]` header rendered wrong in
light mode. 48 commits, deployed continuously to production.

## 1. The reported defect

`PolicyHero` is dark in **both** themes — `bg-[#111111]`, `text-white`,
`border-white/15`, not one `dark:` variant in the file. It is a deliberate dark
hero, not a themed surface.

Its status chip, though, came from `getStatusColor()`, which returns light/dark
**pairs**. That helper is right for a themed surface (`KeyDatesCard`'s `pw-card`,
the customers page's `bg-white dark:bg-neutral-800`) but on an always-dark hero
the light half wins whenever the app is in light mode — rendering a
`bg-green-50` / `text-green-700` chip, styling meant for a white page, onto a
black slab.

**Fix:** `getStatusColorOnDark()` alongside it, following the on-dark chip idiom
the hero already used for its renewal and gap badges. `KeyDatesCard` and the
customers page keep the paired palette, which is correct for them. Pinned with
5 unit tests.

## 2. Why no audit caught it — the structural finding

Every sweep enumerated static routes from `app/**/page.tsx` and **explicitly
skipped the 17 dynamic ones** as "covered by the journey specs". The journey
specs do not check theming. `/wallet/[id]` had never been rendered by any audit,
so a 100%-green suite said nothing about it.

Worse: when discovery was added, `/wallet` still yielded nothing, because the
wallet navigates with `router.push()` on a card click rather than an `<a href>`.
Discovery now falls back to the app's own API with the session cookie.

  gradient in dark mode; its sibling `.pw-page-shell` had had a `.dark` override
  all along. A gradient paints via `background-image`, so a computed
  `backgroundColor` check reports `transparent` and never sees it.
- 140 light-only surfaces paired with dark partners across 53 files
- 21 unpaired `text-[#92400E]` (dark text on `dark:bg-amber-900/30`)

## 6. Test infrastructure added

- `tests/theme-state-cascade.spec.ts` — reads the CSSOM for every rule carrying
  a state pseudo-class and computes the contrast that state WOULD produce.
  Covers every element in every declared state in 15 min; the previous approach
  (driving real mouse events) never finished.
- `tests/ui-quality-audit.spec.ts` — 108 routes x 9 widths, loading once and
  resizing.
- Admin fixture (`E2E_ADMIN`) + `admin-chromium` project — the admin console had
  never been rendered by any audit.
- **Vacuity floors on every suite.** Each asserts a minimum scanned count, so a
  harness fault fails loudly instead of reporting green.

## 7. Five corrections — all mine, not the environment's

1. **"Dev DB unreachable"** — a missing `DIRECT_URL` in the shell. This had me
   record the admin fixture as impossible for several rounds.
2. **"No fixture policy exists"** — two do. I queried `Policy.userId`; the column
   is `ownerUserId`.
3. **A specificity regression I introduced** — `.grid > *, .flex > *
   { min-width: 0 }` as a plain selector outranked legitimate `min-w-*`
   utilities and silently clamped a deliberate `min-w-[24px]` to 21px. Rewritten
   as `:where(...)`. **A safety net must never outrank a deliberate value.**
4. **Duplicate `dark:` classes** left by my own codemod.
5. **`/account` "no hover feedback" x11** — the snapshot returned `undefined`
   and `undefined === undefined`. Eight rounds lost. The tell was a finding count
   that stayed byte-identical at 188 across five different edits: **a number that
   does not move when the code moves is not measuring the code.**

## 8b. The defect that shipped twice — and the guard that ends it

The reported bug had TWO instances in one component, both light-mode-only:

1. The status chip drew from `getStatusColor()`, which returns light/dark pairs.
2. The three action buttons used `.pw-secondary-button`, whose colour is
   `var(--pw-text-primary-light)` and only flips via `.dark .pw-...`.

`PolicyHero` is `#111111` in BOTH themes, so a themed page-surface class
inherits the LIGHT half whenever the app is in light mode — dark text on a
near-black card. **In dark mode both looked correct**, which is precisely why
every automated theme sweep missed them and why both user screenshots were light
mode.

`tests/unit/always-dark-surfaces.test.ts` now asserts that components whose
surface is dark regardless of theme use no themed page-surface class or helper.
It also asserts its own premise and that the on-dark alternatives exist, so it
cannot become vacuous.

**Verified by reintroduction**: putting `.pw-secondary-button` back on one
button fails the suite with a message naming the cause; restoring it goes green.

**Verified visually and by measurement** (light mode, rendered):

| control | contrast |
|---|---|
| Ρωτήστε το AI (mint fill) | 9.59:1 |
| Κοινοποίηση σε σύμβουλο | **18.88:1** |
| Λήψη ασφαλιστηρίου | **18.88:1** |
| Επικοινωνία με ασφαλιστή | **18.88:1** |

Screenshot: `test-results/hero-light.png`. The three that were invisible now
render white on `#111111`.

**Harness note:** every earlier verification attempt died because Playwright's
`webServer` starts `npm run dev`, and the first hit on each route pays on-demand
compilation. Running `npx next start` against the production build first — the
config already has `reuseExistingServer` — turned a run that never finished into
one that completes in 1.4 minutes. Worth doing for any future audit run.

## 9. The durable lesson

Every defect this audit found came from a component that **bypassed the design
tokens**. Components using tokens were correct automatically.

And the audits themselves were wrong more often than the product was. Four of
the last five "defects" were measurement failures reported as component
failures. Hence the vacuity floors: a suite that stops measuring must fail, not
go quiet.
